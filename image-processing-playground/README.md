### How a request flows

1. The visitor picks an image. `static/script.js` keeps the `File` object in memory and shows a
   preview straight from it, without uploading anything yet.
2. Whenever the mode changes (immediately) or a slider moves (after a 250 ms debounce), the script
   builds a `FormData` holding the image, the operation name and only that operation's parameters,
   and sends it to `POST /api/process` with `fetch`.
3. `app.py` validates the request. Anything wrong with it returns a 400 with a JSON error message.
4. The image is decoded in memory with `cv2.imdecode`, shrunk so its longest side is at most 1400
   pixels, run through one OpenCV operation, encoded as a JPEG and returned as
   `{ "image": "data:image/jpeg;base64,...", "message": "..." }`.
5. The script shows the image and the message. A request counter makes it ignore any reply that is
   older than the latest request, so a slow reply cannot overwrite a newer result.
6. The result is added to the history, which lives in the browser.

One Flask app serves both the page and the API, so there is a single Render service and no
cross-origin setup.

### Files

| File | Responsibility |
|---|---|
| `app.py` | The two routes, request validation, and every OpenCV operation |
| `templates/index.html` | Page structure: upload area, mode picker, sliders, the two image cards, explanation, history |
| `static/script.js` | Upload handling, calling the backend, debouncing, error messages, history |
| `static/style.css` | Layout and styling, including the phone-width rules |
| `static/scottie.svg` | The header illustration |
| `requirements.txt` | Flask, NumPy, opencv-python-headless, gunicorn |

### API

`GET /` returns the page.

`POST /api/process` takes `multipart/form-data`:

| Field | Required for | Allowed values |
|---|---|---|
| `image` | every request | a `.jpg`, `.jpeg` or `.png` file of at most 10 MB that OpenCV can decode |
| `operation` | every request | `original`, `grayscale`, `blur`, `edges`, `sharpen`, `hough` |
| `sigma` | `blur` | 0.5 to 5.0 |
| `low_threshold`, `high_threshold` | `edges` | 0 to 255 each, and high must not be below low |
| `max_lines` | `hough` | 1 to 30 |

| Status | Meaning |
|---|---|
| 200 | `{ "image": <JPEG data URL>, "message": <note for the user, may be empty> }` |
| 400 | `{ "error": ... }`: missing file, wrong extension, undecodable image, unknown operation, or a parameter that is missing, not a number or out of range |
| 413 | `{ "error": ... }`: the upload is larger than 10 MB |
| 500 | `{ "error": ... }`: something failed during processing |

### Operations

| Mode | What the backend does |
|---|---|
| Grayscale | `cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)` |
| Gaussian Blur | `cv2.GaussianBlur` with kernel size `(0, 0)`, so OpenCV derives the kernel size from sigma |
| Edge Detection | grayscale, a light 5x5 Gaussian blur to suppress noise, then `cv2.Canny(low, high)` |
| Sharpen | `cv2.filter2D` with the gentler 3x3 kernel `[[0,-0.5,0],[-0.5,3,-0.5],[0,-0.5,0]]`; the weights sum to 1 to preserve brightness in flat areas |
| Hough Line Detection | Canny at 50/150, then `cv2.HoughLinesP` (1 pixel and 1 degree resolution, 50 votes, minimum length one tenth of the shorter side, gaps up to 10 pixels); the longest `max_lines` segments are drawn in cyan on a copy of the image |

### History

The history is stored in the visitor's browser under the `localStorage` key
`image-playground-history-v1` and is never sent to the server. Each entry holds the file name, the
mode, its settings, the time, and two JPEG thumbnails (original and processed) drawn on a canvas at
no more than 320 pixels per side. There is one entry per image and mode, so moving a slider updates
an entry instead of adding more, and only the 12 newest entries are kept. The "Original" mode is not
recorded. A real photo takes roughly 50 KB per entry.

### Running locally

```bash
cd image-processing-playground
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python app.py
# then open http://127.0.0.1:5001
```

The local port is 5001 because macOS uses port 5000 for AirPlay.

### Deployment

The app runs as a Render web service that deploys from the `main` branch of this repository.

| Setting | Value |
|---|---|
| Language | Python 3 |
| Root Directory | `image-processing-playground` |
| Build Command | `pip install -r requirements.txt` |
| Start Command | `gunicorn app:app` |
| Environment variables | none |

Because of the Root Directory setting, only changes inside this folder trigger a redeploy. Render
passes the port in a `PORT` variable, which gunicorn reads by itself. The free instance goes to
sleep after 15 minutes without traffic, and the next visit takes about a minute to wake it.

### Secrets and uploaded images

The project has no API keys, passwords or other secrets, and uses no environment variables or
third-party services. The code never writes an uploaded image to disk: it is decoded, processed and
returned within one request. Flask may buffer an upload larger than about 500 KB in a temporary
file while it is being received, and deletes it when the request ends. The Flask debug server only
runs under `python app.py` on a developer's machine; Render starts the app with gunicorn.

### Known limitations

- Hough line detection works well on images with clear straight edges and poorly on cluttered
  photos, where it finds short segments and often several near-duplicates along one edge.
- The whole image is uploaded again on every change, which is simple but slow on a weak connection.
- The result is always a JPEG, and transparency in a PNG is dropped.
- An image under 10 MB with a very large pixel count is fully decoded before it is shrunk, which
  could exhaust the 512 MB of Render's free instance.
- History cards are a read-only record. They hold thumbnails only, so a past result cannot be
  reopened at full size, and the history does not follow the visitor to another browser or device.

### How it was tested

- **Backend, with curl:** every operation on valid input, edge cases (a blank image, an 8x8 image,
  a 5000x3000 image) and 16 invalid requests, both locally and against the deployed service.
- **Page, in Chrome:** upload, drag and drop, every mode, the slider debounce (40 rapid events
  produced one request), the two threshold sliders pushing each other, each error state, a late
  reply not overwriting a newer one, and the history (adding, replacing, surviving a reload, the
  12-entry limit, clearing, corrupted stored data).
- **Layout:** checked at 390 pixels wide in a desktop browser. It has not been checked by Claude on
  a physical phone.
